# Архитектура и инварианты безопасности

## Назначение

`x-tuna` запускается после ручной установки LucX, создания администратора,
inbound’ов и подготовки сертификатов. Скрипт обнаруживает фактическую топологию,
формирует manifest, показывает план и управляет только внешней интеграционной
обвязкой и явно разрешёнными публичными метаданными.

Управляемые компоненты: HAProxy TCP/SNI, Nginx-заглушки, системный DNS,
изолированная nftables table, logrotate, certificate reload hooks,
необязательный subscription-sidecar, Cloudflare origin guard и update-worker.

## Граница состояния LucX

Обычная транзакция может менять только:

- `settings.webDomain`;
- `settings.subDomain`;
- `settings.webBasePath`;
- clean subscription URL settings;
- `share_addr` выбранного публичного inbound’а;
- включённые Host endpoints выбранного inbound’а;
- пути сертификатов панели и подписки после отдельного подтверждения.

Никогда не записываются клиенты, inbound’ы, outbounds, transport, credentials,
UUID, `subId`, внутренние порты, содержимое сертификатов и исходный Naive
Caddyfile. Последний только читается и контролируется по hash/metadata.

## Жизненный цикл транзакции

```text
read-only audit
    ↓
manifest и план
    ↓
backup
    ↓
staging
    ↓
проверка реальными бинарниками
    ↓
atomic commit
    ↓
перезапуск только нужных служб
    ↓
health-check
    ↓ при ошибке
rollback
```

Каждое изменяющее действие выполняется под эксклюзивной блокировкой и повторно
считывает LucX перед commit. Это защищает от гонки с панелью и устаревшим планом.
Установка APT-пакетов показывается отдельно: файловый rollback не делает её
полностью обратимой.

## Discovery и manifest

`discovery.py` читает ОС, SQLite в query-only режиме, systemd, listeners,
сертификаты, Host rows, transport и SNI. Секретные поля не попадают в audit
manifest. `migrations.py` преобразует старые v1/v2 в v3 в памяти. Более новая
неизвестная схема доступна только для read-only аудита и блокирует mutation.

Manifest описывает обнаруженное состояние и намерение оператора. Он не должен
использоваться как резервная копия базы и не должен содержать credentials.

## Сетевая модель

Фиксированный набор протоколов не предполагается. Каждый включённый inbound
обрабатывается отдельно. TCP и UDP являются независимыми пространствами портов:
TCP/443 может принадлежать HAProxy, а UDP/443 одновременно Hysteria2.

Семейство L4 определяется transport:

- mKCP и legacy QUIC используют UDP;
- WebSocket, gRPC, HTTPUpgrade и XHTTP используют TCP;
- raw stream проверяется по фактическому transport;
- неизвестный transport отображается, но не получает маршрут по догадке.

Внутренний порт LucX не заменяется внешним портом. Прямая публикация без NAT
допускается только при совпадении public и listener port. Смешанный inbound
хранит отдельный `udp_public_port`.

## TCP/SNI и заглушки

HAProxy владеет явно выбранным публичным TCP-портом, Nginx слушает только
loopback. В строгом режиме существующий протокольный SNI всегда имеет приоритет:
скрипт не перехватывает его ради сайта.

Каждый уникальный домен классифицируется как один из статусов:

- `direct_tcp_decoy` — свободный TCP-маршрут можно направить в Nginx;
- `udp_with_tcp_decoy` — VPN остаётся на UDP, TCP-заглушка безопасна;
- `reality_endpoint_decoy` — endpoint отличается от camouflage SNI;
- `existing_fallback_observed` — существующий fallback только наблюдается;
- `naive_caddy_owned_readonly` — домен принадлежит нетронутому Caddy;
- `blocked_sni_collision` — SNI занят VPN и перехват запрещён;
- `unsupported_safe` — топология неизвестна, автоматическое изменение запрещено.

`default_server` и unknown-SNI маршрут включаются только явным выбором. Каждый
управляемый сайт получает собственный маркер ответа и проверяется по HTTPS.

## Transport-specific split

Расширенный режим является отдельным подтверждаемым режимом и не включается
автоматически. Разделение разрешается только при доказанных признаках:

- XHTTP — dedicated non-root path и его descendants идут в VPN, корень идёт в
  заглушку;
- WebSocket/HTTPUpgrade — проверяются путь и Upgrade-заголовки;
- gRPC — проверяется `Content-Type`;
- бинарный TLS — HTTP-префикс проверяется до повторного TLS-соединения;
- Reality — endpoint и camouflage SNI различаются;
- TrustTunnel — проверяется точный Client Random matcher;
- Naive — используется native или отдельный управляемый frontend.

Неоднозначный транспорт блокируется, а не отправляется в VPN или заглушку по
эвристике. Путь XHTTP `/` запрещён, поскольку невозможно сохранить браузерный
корень без изменения inbound’а.

## Naive

Исходный LucX Naive Caddyfile никогда не изменяется. Перед применением и после
него проверяются содержимое, тип, владелец, режим и hash.

Если обнаруженная конфигурация умеет одновременно proxy и file delivery, она
остаётся владельцем домена. Иначе может быть создан отдельный управляемый
frontend с тем же обнаруженным binary и разрешёнными proxy-параметрами. Этот
frontend является отдельным файлом и systemd-службой; он не переписывает
исходный Caddyfile.

## Подписки и sidecar

Sidecar loopback-only, fail-open и включается только после отдельного согласия.
Он читает безопасные метаданные базы в режиме read-only.

- qWDTT и `wdtt` исключаются из подписок;
- TrustTunnel QUIC/HTTP3 исключается, остаётся TCP/HTTPS `h2`;
- Throne получает AWG `wg://` с корректными CIDR и Base64;
- Throne получает Mieru `traffic-pattern` без ошибочного `%2F`;
- AnyTLS получает public Host domain/port вместо internal listener port;
- имена, fragment и credentials сохраняются;
- Clash/Mihomo и неподдержанные ответы проходят без опасного преобразования;
- при ошибке преобразования возвращается исходный ответ LucX.

Удаление sidecar разрешается только для неизменённых файлов, которые ранее
создал сам конфигуратор. Пользовательский или изменённый файл блокирует удаление.

## TrustTunnel backend

Отдельный backend отключён по умолчанию. Он принимается только после pinned
binary probe и protocol-level проверки TCP, TLS 1.3, ALPN `h2`, HTTP/2 `CONNECT`,
обычного GET/HEAD и неверных credentials. Backend запускается на loopback и
получает hardened systemd unit. Public 443 не переключается до успешного
CONNECT health-check.

LucX TrustTunnel может требовать Client Random prefix, поэтому обычный binary
нельзя автоматически считать совместимым с новым маршрутом.

## Cloudflare

Origin guard применяется только к панели и подписке, если оператор подтвердил
orange-cloud DNS. CIDR IPv4/IPv6 загружаются с официальных Cloudflare endpoints
перед commit, проверяются и обновляются ежедневным timer’ом. Список не хранится
константой в установщике.

HAProxy и nftables отклоняют не-Cloudflare источники только для panel/subscription
маршрутов. VPN SNI на общем TCP-порту остаются публичными.

## Сертификаты

Скрипт проверяет готовые сертификаты или отдельно, после подтверждения, выпускает
сертификат через Certbot DNS-01. API token не попадает в argv, журнал или report.
Проверяются SAN, wildcard, срок действия, соответствие private key и права файла.
После отдельного подтверждения активные пути и renewal hook меняются транзакционно.

Reality camouflage SNI не добавляется в список сертификата без необходимости.

## Firewall и обновления

Основная nftables table изолирована и не очищает host ruleset. При подтверждённом
маршруте TrustTunnel через 443 его внутренний listener блокируется извне по TCP
и UDP, но loopback для HAProxy сохраняется.

Официальный updater LucX выполняется в отдельном `lucx-post-update@.service`.
Перед обновлением создаются backup и pending marker. Worker записывает фазы,
запускает updater, затем repair и удаляет marker только после успеха. При reboot
постоянная repair-служба продолжает восстановление.

## TUI

TUI является проекцией того же engine. Все пункты и подтверждения цифровые.
Перед изменением показываются файлы, поля базы, службы, backup, защищённые
объекты и исключённые маршруты. JSON предназначен для CLI/report и не выводится
как сырая структура в интерактивном меню.

Для известного числа этапов показывается процент. Для APT, загрузок и внешнего
updater показываются текущая фаза, heartbeat и прошедшее время без выдуманного
процента.

## Backup, integrity и отчёты

До изменений создаётся предварительный backup, после подготовки пакетов —
операционный baseline. SQLite snapshot консистентный, root-only и предназначен
для ручного аварийного восстановления. Reports редактируются централизованно:
пароли, токены, UUID, subId, URI, ключи и большие payload заменяются отпечатками.

Production backup, database snapshot и реальные отчёты никогда не публикуются в
GitHub.
